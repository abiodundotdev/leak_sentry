## 0.0.1

The detection pipeline: watch disposed objects, wait, check, then dump and analyze what is still retained.

* **Object watcher.** `State`, `Route`, `ChangeNotifier` and `AnimationController` are watched when Flutter disposes them, through one shared listener on `FlutterMemoryAllocations`. After a retained delay (5 s) an object that is still reachable is *retained*. `LeakSentry.objectWatcher` (`ObjectWatcher`, `RetainedObjectTracker`, `DeletableObjectReporter`, `InstallableWatcher`) watches anything else.
* **Heap dump trigger.** A retained object schedules a check (only one can be pending): force a GC, count again, then wait for 5 retained objects while the app is visible (rechecking every 2 s), dump after the retained delay once it is in the background, never dump twice within 60 s, retry a failed dump after 5 s. `LeakSentry.dumpHeap()` dumps on request.
* **`LeakSentry.install()`** (once; refuses release builds unless `allowInRelease`), `installObjectWatcher()` for release builds, and `LeakSentryConfig` (`dumpHeap`, `retainedVisibleThreshold`, `enableRetainingPathAnalysis`, `maxRetainingPathLookups`, `heapDumper`, `eventListeners`). Heap dumping is off under `flutter test`.
* **Events.** `DumpingHeapEvent`, `HeapDumpEvent`, `HeapDumpFailedEvent`, `HeapAnalysisProgressEvent`, `HeapAnalysisSucceededEvent`, `HeapAnalysisFailedEvent`, through `LeakSentryEventListener`s and `LeakSentry.events`.
* **The GC is not repeated for nothing.** It is skipped when every retained object became retained before the last forced GC started (Dart's GC pauses the app), and always runs before a dump.
* **Analysis.** Retained objects are grouped by type, reason and creation site, and the VM service supplies one retaining path per distinct leak.
* **Unclosed resources.** `TrackedStreamController` and `LeakSentry.trackResource` report a resource that is garbage collected without being closed.
* `LeakSentry.stats` (`LeakSentryStats`) counts what detection costs.
* `await LeakSentry.dumpHeap()` completes once the leaks of that dump are in `leakHistory`, so `expectNoLeaks()` can follow it. `LeakSentry.runGc()` forces a GC (verified through the VM's reachability barrier).
* Retaining paths name static fields (`Holder._graveyard (static)`), and an object nothing retains any more is counted as unreachable instead of being reported as a leak.
* The connection to the app's own VM service is re-opened at the current address when it is lost (the Flutter tool's service takes over a moment after startup), tries the emulator's host address on Android, and pauses for 15 s after a failure.
* On the web `install` only counts retained objects; a GC that throws, a dump that never answers or a listener that holds up the events no longer wedges the checks (limits of 30 s, 30 s and 10 s).
* Per-object "Watching instance of …" log lines are off unless `LeakSentryLog.verbose` is set: Flutter disposes hundreds of objects on each navigation.
* **Screens.** `LeakSentryOverlay` shows a badge with the number of leaks, and a notice while objects are held but not yet scanned. Tapping it opens the LeakSentry screen: **Leaks** (the distinct leaks), **Scans** (each heap scan, with **Scan now**) and **Settings** (scan automatically, how many held objects to wait for, clear). `LeakSentry.showScreen([context])` opens it from anywhere; `LeakSentryScreen` can be embedded. It is a route of the app's navigator, so dialogs, back and text selection work in it.
* **The creation call site is always visible.** Every leak says where its object was created (`LeakReport.creationSite`, `Created at`), else where it was handed to `objectWatcher.watch` (`watchSite`), else where its class is declared (`classSite`), else why none is known (`CreationSiteGap`). A resource that was never closed says where it was acquired. It is in the list rows, the detail screen (for every instance), the scans, the copied and printed report, and `LeakReport.toString`.
* **The trace.** `LeakReport.trace` (`LeakTrace`) works the retaining path out: each step named as written in code, a status for each (`NodeStatus.inUse`, `shouldBeGone`, `unclear`) and why, the likely-cause references marked, and a `fingerprint`. Steps are told apart structurally (static variables, Dart's event loop, framework singletons, other watched objects) and by their fields as the VM reports them (`State`, `Element`, `Route`, `ChangeNotifier`, `AnimationController`, `RenderObject`). A closure and its captured variables are one step; list and map hops are `[x]` and `{key}`.
* **Distinct leaks.** The screens group leaks by the fingerprint of their trace, so what is held by the same likely cause is one leak whatever it is, and a leak is called by its likely cause (`PageRegistry.pages`). `LeakSentry.leaks`, `leakHistory` and `expectNoLeaks` keep their first-report-per-signature behaviour.
* Exports: `LeakSentryScreen`, `LeakSentryTab`, `LeakTrace`, `TraceNode`, `TraceReference`, `NodeStatus`, `CreationSiteGap`, `RetainingPathGap`, `RetainingElement`, `LeakSentryInternal`. `LeakReport` gained `trace`, `watchSite`, `classSite`, `creationSiteGap` and `pathGap`.
* LeakSentry's own `State`s, routes and notifiers implement `LeakSentryInternal`, and are never watched.
* **What the analysis holds.** The VM keeps an object alive for as long as it has an id for it, so each retaining-path lookup, and the reads of the fields of the objects on its path, run in an id zone of their own that is emptied once the leak has been worked out, and used again by the next lookup. An analysis therefore no longer goes on holding what it looked at (a VM that has no zones gets the old behaviour). A zone is emptied, never deleted: deleting one makes the Dart VM of 3.6 to 3.10 (Flutter 3.27 to 3.38) crash at its next garbage collection. Lookups and reads time out (30 s and 10 s) instead of waiting for a VM that is not going to answer.
* Resources that were never closed and share a label are different leaks when they were acquired in different places, each with its own `Acquired at`. `LeakSentry.showScreen(context)` with a context above the app's navigator opens the screen through the overlay instead of throwing. The overlay no longer keeps the navigator it found.
* Removed from the earlier internal version, which was never published: `LeakTracker`, the `tracker:` parameters of `LeakSentry` and `LeakSentryOverlay`, `LeakConfidence.disposalTimeoutExceeded`, the periodic sweep and its configuration options, the forced-GC rate limiter, the frame-activity gate and the wall-clock fallback.
